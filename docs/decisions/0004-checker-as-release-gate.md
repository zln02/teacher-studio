# 0004. 점검기를 출시 관문으로 쓴다

- 상태: Accepted (2026-11-18)

## 배경
선생님은 깨진 결과를 받아도 원인을 모르고, 오래된 학교 전자칠판의 크롬은 최신 문법을 못 읽는다. 「만들었다」와 「수업에서 돌아간다」 사이에 검증이 필요하다.

## 결정
결과물은 **점검기를 통과한 것만 보여 준다.** 점검은 두 겹이다.
1. **정적 검사**(`check_page.py`/`check_game.py`): ES2017 위반(`?.` `??`), 외부 이미지·자원, 학생 정보 입력칸, spec 규칙, 토큰 대비·글자 하한, 정답 위치 편향 경고.
2. **헤드리스 autoplay**: 브라우저로 게임을 끝까지 자동으로 플레이해 결과 화면 도달, JS 오류, 화면 넘침, 작은 글씨를 확인.

브라우저는 Playwright Chromium → 시스템 Chrome → Edge 순으로 시도하고, 모두 없으면 **정적 검사만으로 WARN과 함께 진행**한다(실패로 막지 않고 한계를 알림).
오류 문장은 「코드 몇 번째 줄」이 아니라 **spec에서 무엇을 고칠지**로 쓴다(예: 항목 수·정답 번호 확인).

## 검토한 대안
- **수동 확인만**: 선생님이 직접 못 하고 AI도 놓침. 기각.
- **Playwright 필수화**: 설치 부담이 크고 Claude 앱 같은 샌드박스에서 불가능. 기각 — 폴백 유지.
- **점검 실패해도 결과 전달**: 깨진 자료가 수업에서 발견됨. 기각.

## 결과
- 장점: 문제가 만든 시점에 잡힌다. 기본 빌드(`build.py`)가 자동으로 점검을 돌려 AI가 따로 기억할 필요가 없다. 같은 점검기가 회귀 테스트(`examples/baseline/run_baseline.py`)에도 쓰인다.
- 단점: autoplay는 환경에 따라 건너뛰어질 수 있다(그때는 정적 검사 수준 보증). 점검 통과가 「재미있다」를 보장하지는 않는다.
- Windows cp949 콘솔에서 점검 출력이 깨지던 문제는 stdout 재설정으로 해결(커밋 `bdc8475`).
