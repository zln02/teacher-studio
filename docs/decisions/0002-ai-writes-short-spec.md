# 0002. AI는 코드 대신 짧은 JSON spec을 쓴다

- 상태: Accepted (2026-11-18)

## 배경
선생님은 한 줄로 요청하고, 무료 요금제처럼 사용량이 한정된 환경에서도 쓴다. AI가 게임 코드를 매번 처음부터 쓰면 토큰이 많이 들고, 오래된 학교 크롬에서 깨지는 문법·글자 겹침 같은 실수가 반복된다. 같은 요청에도 결과가 달라진다.

## 결정
AI의 산출물은 **내용 + 방식(mechanic) + 디자인 방향**만 담은 짧은 spec JSON 한 장이다(`skills/teacher-game/references/spec-schema.md`, 형식은 `spec.schema.json`). 엔진·부품·디자인·점검은 코드(도구)가 맡는다. **맞는 부품이 없을 때만** 가장 가까운 component를 복사해 새 부품 하나를 직접 코드로 추가한다.

## 검토한 대안
- **AI가 HTML/JS 전체 작성**: 유연하나 토큰 낭비, 첫 시도 통과율 낮음, 재현 불가. 기각.
- **완전한 스킨 JSON 작성**(기존 방식): 장면·그림까지 포함해 크고(2.6~5.7KB) 종류 확장이 안 됨. 기각(ADR 0001).
- **자연어 → 폼 UI**: 이 저장소는 UI 없는 스킬 묶음이라 범위 밖. 기각.

## 결과
- 장점: 출력 토큰이 작다. spec은 `specs.py`가 먼저 검증해 「고칠 곳」 문장으로 돌려주므로 첫 시도에 막혀도 한 번에 고친다. 같은 spec이면 같은 결과(결정성).
- 단점: spec이 표현하지 못하는 기발한 요청은 맞는 mechanic을 찾기 전까지 대체 방식으로 안내하거나 직접 코드가 필요하다(더 느리고 점검 부담이 큼). 부품 수가 곧 표현 범위다.
- 트레이드오프: 자유도를 일부 포기하고 일관성·비용·검증 가능성을 얻는다.

## 근거/측정
- spec 크기: `examples/baseline/spec-builds.json` 기준 611~2,514 B (신규 예제 7개 611~1,801 B). 같은 종류 스킨 JSON은 2.6~5.7KB.
- 결과 HTML: 레거시 빌드 153~159KB → spec 빌드 약 98~102KB (`game-baseline.json` vs `spec-builds.json`).
- 첫 시도 통과율(first-try pass rate)은 아직 체계적으로 측정하지 않았다. 현재 증거는 예제 spec 9개가 빌드·점검 모두 PASS라는 것뿐이며, 통계적 주장은 하지 않는다.
