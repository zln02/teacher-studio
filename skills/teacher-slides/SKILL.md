# 교사 스튜디오 · 슬라이드

Run the scripts as written with `python3`; on Windows type `py` instead (no `py`: `python`). Always the short command name, never an interpreter's full path (`C:\...\python.exe`).

Teacher (no coding) asks in plain words for a PPT / talk / training / parent-meeting / club deck. You write a **short JSON spec**; tools design it, check it, and screenshot it.
Principle: tools guarantee the floor (type scale, contrast, safe margins, keep-all Korean, density), you add the message - and the floor is not the ceiling (`shared/content/CONTENT-RULES.md`, 「Floor, not ceiling」): never a thinner or plainer deck than you would make without this skill. Restraint beats decoration, but restraint is about ornament, not about content: one claim per slide, one main colour with at most two marker colours (picked by the tools by default; the user's palette, or a palette and drawings you can justify for this topic, may replace them and must still pass the gate). One claim is not one box: when the claim needs two or three pieces of evidence (the figures and the chart behind them, a drawing and the rule it shows), they sit together on that slide (`panel`).

Respond in the user's language. Follow the ask-first rule: `../teacher-studio/references/ask-first.md`.
The user's own template or reference comes first. (The user-template weapon - building from a PPT/design the user supplies - is planned, not built yet. Colours are covered: `shared/design/color_from.py deck.pptx --out pal.json`, then `"design": {"palette_from": "pal.json"}` in the spec, see `../teacher-studio/references/user-colors.md`; the composition stays ours. For type and layout learn from the file via `../teacher-studio/references/learn-from-reference.md` and say honestly that it is an approximation, not a copy.)

Content quality first: before writing any content read references/content-slides.md; pass the expert gate in shared/content/CONTENT-RULES.md.

## Words
- Never show code or file names to the teacher. 「PPT 만들어 줘」「칠판에 띄울 거」「글씨 더 크게」 -> `references/teacher-language.md`.
- **Editable PowerPoint** (「PPT」「파워포인트」「피피티」「.pptx」, or 「나중에 내가 고칠 거예요」) -> ALWAYS deliver an editable `.pptx` next to the web deck: add `--pptx` (same spec, same look; real text boxes, native charts and tables, speaker notes, QR as shapes). Say honestly what changes in PPT: 「단계별 나타나기·타이머·수식은 단순해져요」 (icons are drawn in the .pptx too, as editable outlines) and 「글꼴은 PC에 없으면 비슷한 글꼴로 바뀌어요」. python-pptx is installed on first need only after the teacher says yes (`shared/tools/ensure.py`, `--yes`). The teacher's own `.pptx/.potx` -> `--pptx --template mine.pptx` (their masters and layouts are used: template first). If the official `pptx` skill is listed by `doctor` (`official_doc_skills`) you may hand the file work to it for extras (animations, SmartArt, tracked edits); we still bring the structure, design and checks. PDF: 「Ctrl+P → PDF로 저장」.
- Intro video / countdown -> teacher-motion. Quiz game -> teacher-game.

## Pick the context from the request (one spec key)
`"context"`: **class** (수업·차시·학습 목표) · **promo** (홍보·모집·축제·알리기) · **public** (기관 보고·업무 보고·교육청·결과 보고) · **personal** (가족·자기소개·동호회·여행). It switches layouts, type scale, palette, numbering and slide defaults for the web deck and the .pptx; unsure -> ask once in the first question ("수업용 / 홍보용 / 기관 보고용 / 개인용"). Public = 표지(`org`,`date`,`dept`) + auto 목차 + `summary` + Ⅰ./1. + 개조식 + `table` + `source` on every data slide (required). Class = `objectives` + quiz/activity + `recap`. Promo = `hero` + CTA/QR. Personal = photo `hero`. Details, keys, sources: `references/context-recipes.md`. A user template still wins (`--template`, `palette_from`).

## A PowerPoint file was asked for (「PPT」「파워포인트」「.pptx」): the short path
One command builds the .pptx, checks it and draws the preview: `python3 scripts/deck.py --spec deck.json --pptx 발표.pptx --pptx-only --review review/` (drop `--pptx-only` and add `--out deck.html` when the web deck is wanted too).
1. Write the spec with the **content recipe** below (context, real structure, figures, check questions with answers). 「알아서」 = no questions: what the user did not give is filled with plausible example values, each written into `"fillins"` (rule: 「Unknown facts」 below).
2. Run the command. Read every `FIX` / `FAIL` / `NOTE` line.
3. **Look once**: open `review/<name>-approx-sheet.png` (all slides, drawn from the pptx: shapes, lines, tables, charts, pictures). If the build printed `NO-BROWSER` (no screen can open in this environment) the picture is `review/<name>-sketch-sheet.png` instead, a rougher drawing made without a browser: look at that one, do not try a browser or draw your own preview, and say in the last message that the screen was not opened. Thin or plain slide -> give it its evidence (`diagram`, `table`, `chart`, `compare`, `activity`) or fold it into its neighbour as a `panel`; a slide that leaves half the screen empty, or three list slides in a row, is not finished. Never ship a text-only deck.
4. **Hard gate, last step, always:** rerun until the build prints `READY 발표.pptx`. `NOT DONE` / any `FAIL pptx:` line = not finished: fix the spec and run again (max 3 loops, then say plainly what still fails). Never write 「다 됐어요」 while it FAILs. A .pptx made or edited any other way (by hand, by another skill, after a fix request) goes through the same gate: `python3 scripts/pptx_check.py FILE.pptx --render review/` until `RESULT: PASS`.
5. Last message: the file in the folder the user named (current folder if they said so), the 「바꿔 넣을 곳」 list (every example value from `"fillins"`, as the build printed it), and that the picture was an approximate preview.
Working alone or handing the job to a helper agent, the recipe and the gate travel with it: put this skill's name and step 4 in the hand-off.

## Content recipe (what makes the deck worth using)
- **Every body slide carries three things** (all contexts): a title that is the claim or the question, the evidence, and - where the audience could miss the point - the conclusion in one line (`"takeaway"`: a band under the body; works on `bullets` `compare` `steps` `timeline` `bignumbers` `table` `chart` `panel`). One kind of evidence that fills the screen -> the simple type. A claim that needs two kinds -> **`panel`** (2-4 blocks on one slide: `kpis` + `chart`, `diagram` + `cards` + `note`, `table` + `flow`, `tree` + `note` ...). Do not spread one claim over two thin slides, and do not put two claims in one panel.
- **Depth before brevity.** A deck is judged first on what it teaches or proves. Bring what a strong teacher's or reporter's own deck would have: a source to read with its citation (사료·본문·자료: `quote` + the question it answers, or a `panel` of `note` + `cards`), the process step by step, a worked example, a drawing of the thing itself (`diagram`, `title.shapes`, `flair.svg`), two or three check questions (not one) with answers and reasons, and the sources on the closing slide or in the notes. The per-slide limits below keep one screen readable; they are not a limit on the deck: more to say -> another slide or a `panel`, never fewer facts. When `target_slides` is tight, merge with `panel`; do not drop a sub-topic, a person or a term the unit names.
- **Coverage list first, then the spec.** Write down everything the unit (or the report) is expected to carry: each sub-topic, the people and terms named in it, and its closing point (의의와 한계, 결론, 다음 과제). Every entry lands on a slide; many names fit one slide as a `table` (누가 · 무엇을 주장 · 근거나 저서). Activities and questions do not replace coverage: in a lesson deck of about ten slides they are at most a third, each with its answer or an example answer on a slide. A box that holds one short line inside a large frame reads as unfinished: give every card its second level (the detail, the example) or use fewer, fuller boxes.
- **Specific beats tidy.** Each slide names real things: the actual example, place, date, figure with its unit, the term as the textbook or the field writes it, a worked case. Text has two levels (a short heading + its detail: `cards` items `{title, items}`), not one long line per bullet. If a slide could be shown for another topic unchanged, it is not written yet.
- **The deck must not look the same on every slide.** Count the slide types after writing the spec: no type more than a third of the body, lists (`bullets`) at most a quarter, and no two neighbours with the same type and shape. The build prints a NOTE when this slips.
- **수업 (class):** a lesson deck needs four jobs done, in the order THIS lesson needs: say what will be learned (`objectives`), open a question, carry each idea, check and close (`quiz` with `answer` and `explain`, `activity` with minutes, `recap`; the .pptx adds ONE 「확인 문제 정답」 slide before the closing). **The outline comes from the unit, not from a list here**: write down the sub-topics the textbook gives this unit, then give each the slide its shape asks for (something drawn in the textbook -> `diagram`; two things side by side -> `compare` / `table`; an order -> `steps`; figures -> `bignumbers` / `chart`; one sentence to remember -> `statement`). Unsure of the type -> `"type": "auto"` and the build picks it from the content (`scripts/deck_shape.py`). Never drop a sub-topic to make room: when the user names a length (「10장」「10장 정도」) put `"target_slides": 10` in the spec and **land on that number**: the answers slide the .pptx adds counts, so with a check question write 9 slides for 「10장」. One page over is accepted only when it is that answers slide; any other miss prints `WARN 장수:` (fix it: merge neighbouring ideas on one slide, or add the missing one), and far over stops the build. At least half of the idea slides are figures or side-by-side slides, not bullet lists; a drawing and the terms it shows belong on one slide (`panel`: `diagram` + `cards` + `note`), and the cover may carry a small drawing of the topic (`title.shapes`). Facts must be textbook-correct (definitions, units, signs, the direction of every cause and effect). **유치원-초3 (a young room): every key word, example and quiz choice carries its picture** - put ONE emoji in front of it (`"🐶 멍멍: 강아지가 짖어요"`, choice `"⭐ 반짝반짝"`, step title `"✂️ 오리기"`, compare item `"🐮 음매"`) and one on the cover (`"pic": "🌧️"`): the build lifts it out of the text and draws it large beside the word (picture tiles). Never in a title or a sentence; 2-4 picture words per slide; the build prints a NOTE when most idea slides have none.
- **기관 보고 (public):** copy the user's sentence into `"request"` (the build checks that every part it names - 예산, 성과, 계획 ... - has its own content, and that a results report (운영 결과·성과·실적 보고) answers the four things its reader looks for: 실적 in figures, 예산 편성·집행·집행률 as a table, 성과·만족도, 다음 계획; a missing one prints `꼭 담을 내용이 빠졌어요: 「예산」` - add the slide, never drop it silently; extra parts go in `"must": [...]`, one that truly does not apply in `"omit": [...]` and is said in the last message). The reporter is the user's own place (「교육청 보고용」 = our school reports TO the office: `org` 「우리 학교」, not the office). Fixed by convention: 표지(`org`, `date`, `dept`), 목차, 요약 first. The body follows what was done, not a stock list: one `section` per real part of this work (배경·실적·성과·계획 are common names, use the ones this report has), and inside each the slide type follows the data (counts per group -> `table`; a change over time -> `chart`; two or three headline figures -> `bignumbers`; dated plans -> `timeline`; before / after -> `compare`), every one with `source`. Each content slide holds 4-6 lines or a table / chart (`section` entries only name the parts: the .pptx shows them in the header band, not as empty divider pages); more than half are not bullet lists. A report reader compares: put the headline figures and the chart or table behind them on ONE slide (`panel`: `kpis` + `chart`, `table` + `note`), draw who does what as a `tree` and how the work moves as a `flow`, and end data slides with the `takeaway` (what the numbers mean, not what they are). Numbers must agree with each other across slides (20/24 = 83.3 %); the user's own figures they did not give (실적, 예산, 만족도) are plausible example values with a believable `source` (「우리 학교 자체 집계(2026. 11.)」), never a 「확인 필요」「집계 필요」 cell: list them in `"fillins"`, the build notes it ONCE in the first slide's speaker notes (or write one `footnote` under the first data table: 「※ 수치는 예시입니다. 실제 집계로 바꿔 주세요.」), and the last message lists them; a change is written with both ends (「운영 학교 비율 58 % → 81 %, 23 %p 증가」). 개조식 endings.
- **홍보 (promo):** one promise on the `hero`, then only what a reader needs to decide and act: why it is worth it (as many reasons as are real, not always three), the facts to act on (date, time, place: `table` or `timeline` when there are several), one call to action on the closing.
- **회사·모임·동호회 발표 (a look back, a meeting report, a club talk):** the room wants to know how it went and what happens next. Open with the few numbers that matter and their trend on one slide (`panel`: `kpis` + `chart`), name what worked and what did not with the cause of each (not a list of activities), and close with the next actions, each with who and by when (`table` / `timeline`). Figures the user did not give are example values: in `"fillins"`, noted once for the deck (first slide's speaker notes) and listed in the last message.
- **Unknown facts** (one rule for every skill: `shared/content/CONTENT-RULES.md`, 「Unknowns」). What the user gave is used as given. What they did not give (school name, presenter, date, place, cost, their own counts): first choice = **leave it out** when the slide works without it (a lesson cover needs the grade, subject and unit, not a school or teacher name). Where the slide needs one (기관 보고 표지의 기관·부서, 행사 날짜·장소, 실적 수치) write a plausible example value, never a slot and never 「확인 필요」: 「우리 학교」「교육연구부」, a real date with its weekday, a round figure; people as roles, not made-up names. Put each one in `"fillins"`: the build adds ONE line to the first slide's speaker notes (report and promo decks; a lesson deck is simply filled, no note) and prints the list for the last message. No 「교사 초안」 stamp on any slide, and no 「가상」「예시」 in a `source` / `footnote` line: the source names the record (「우리 학교 급식 운영 기록(2026)」), the note is said once (two such lines stop the build). Slots like `(학교명 입력)`, `○○학교`, `OOO`, `[...]`, `(예시)` FAIL the gate. Only when the user asks for blanks to fill in by hand: a labelled underline (`학교: ________`, `교사: ________`), never `○○` / `OO`, plus `"template_blanks": true`.

## Flow
1. **Ask only what is missing, once** (numbered, with defaults): ① who watches (grade / teachers / parents / club) ② topic or source file ③ length (default 10 slides) ④ mood in the teacher's words (따뜻하게, 깔끔하게, 신나게, 힙하게 ...) ⑤ date/presenter line.
2. **Outline table** (번호 | 종류 | 화면 글 | 메모) -> teacher says OK. Skip if they said 「바로 만들어」 (show the table with the result).
3. **Write the spec** (`deck.json`, below) and build:
```
python3 scripts/deck.py --spec deck.json --out deck.html --review review/ [--pptx]      # or: studio.py build slides --spec deck.json
```
   The seed is printed and stored in the file. A first build picks a fresh look; building the same spec file again (a fix round) keeps that look, so what was reviewed is what ships. `--fresh` picks a new look (say so: 「마음에 안 들면 다시 뽑아 드려요」), `--seed N` returns to a given one.
4. **Look.** Open `review/<name>-sheet.png` and judge every slide: *would a professional designer ship this?* Fix the spec (shorter text, other type, `--style`), rebuild, max 2 loops. `check_page.py` + `slides_review.py` must PASS (the build prints both).
5. Show the deck (artifact). Give three fixes in teacher words. Share / PDF / keep-offline lines: 「오른쪽 위 '게시' → 링크」「Ctrl+P → PDF로 저장(배경 그래픽 켜기)」「'다운로드'로 파일 보관, 인터넷 없이도 열려요」. Keys: → / click = next build, ← back, N notes, B black, F full screen, digits+Enter jump.

## Spec
```json
{"purpose":"수업|연수|학부모 설명회|발표|동아리|개인", "audience":"...", "mood":"따뜻하게", "subject":"과학",
 "title":"...", "seed": 7,                       // seed optional
 "design": {"style":"minimal-premium", "builds":true},   // optional overrides
 "slides":[ {"type":"title","title":"..","subtitle":"..","meta":"..","kicker":".."}, ... ]}
```
Words in `**stars**` are emphasised; `\n` breaks a line. Every slide may have `note` (presenter notes), `kicker`, `build:false`, `layout:"bullets.cards"` (force a variant).

| type | keys (limits) |
|---|---|
| title | title, subtitle, meta, shapes (optional: a small drawing of the topic beside the title, same shapes as `diagram`; not on a public cover), icon (optional; without `shapes` the cover shows the topic's icon) |
| section | title, sub |
| statement | text (one big sentence <= 70), sub |
| bullets | title, items 2-6 (<= 60 chars each; 「이름: 풀이」 becomes a bold name + its detail), icons (optional list, one per item); young room: an emoji in front of each item becomes its picture (`pics`) |
| compare | title, a:{label,items}, b:{label,items} or rows:[{k,a,b}] (<= 5) |
| steps | title, steps 3-6 [{title<=18,text<=44,icon}] |
| bignumber | value, unit, caption |
| bignumbers | title, items 2-3 [{value,unit,caption}] (two big numbers side by side = compare) |
| quote | text, source |
| illustration | title, text, motif (Korean/Lucide word), art rings/blocks/arc — geometric, image-free |
| quiz | q, choices 2-5, answer (0-based), explain — next click reveals the answer |
| timeline | title, events 3-6 [{when,title,text}] |
| chart | title, kind bar/line/pie/doughnut, labels, series:[{name,data}], unit, takeaway (Chart.js, inlined) |
| math | tex (KaTeX), text |
| timer | minutes, title — start/pause/reset/±1 min, Space = start/pause |
| qr | url, title, caption — drawn at build time, offline |
| image | file (local path -> inlined, resized to <= 1920px / 3MB), title, caption |
| video | file (<= 8MB embedded, bigger -> 「영상 열기」 button), title |
| closing | title, sub, next[<=4], url (adds a QR) |
| table | title, columns 2-6, rows 1-8 (cells <= 40), unit, highlight, source, footnote |
| summary | title, text, label (핵심), points 2-5 |
| toc | title, items 2-8 (public: filled from sections) |
| hero | headline <= 34, sub, kicker, cta, url (QR), file (photo), facts 0-3 (<= 22 chars each: the things a reader acts on - 날짜, 장소, 비용 - shown on the colour field of the cover), icon |
| panel | title, blocks 2-4, takeaway, layout (`rows` / `cols` / `side`, default automatic). Block = `{"kind": ...}`: `kpis` items 2-4 {value, unit, caption} · `cards` items 2-6 {title, text or items[<=4]} (`"numbered": false` = a filled heading band instead of numbers: terms and their meaning, two sides, kinds) · `list` title, items 2-6 · `chart` chart (bar / line / pie / doughnut), labels, series, unit · `table` columns, rows 1-7, highlight · `note` text, label (the rule, the formula, the caution) · `flow` items 2-6 {title, text} (arrows between) · `tree` root, children 2-5 {title, items[<=3]} (organisation, classification) · `diagram` shapes. Any block may have a `title`. Wide kinds (kpis, flow, note, tree) take a full row, the others sit side by side. Public: `source` needed when a block holds numbers |
| diagram | title, shapes 2-40 on a 100 x 60 canvas: `line` `dash` `arrow` `dasharrow` {x1,y1,x2,y2,color,w} · `rect` {x,y,w,h,fill,text} · `circle` {cx,cy,r (or rx, ry for an oval),fill,text} · `poly` {points [[x,y],..] 3-12 corners, fill, color} (a mountain, a layer, a lens, a roof, a block arrow) · `arc` {cx,cy,r,from,to: degrees, 0 = right, 90 = up} · `label` {x,y,text,color,size s/m/l,align}; colours pr ac tx mu good bad water sky sun or #hex; points 0-4 (notes beside it), caption. Real lines and arrows in the .pptx. Example: `assets/spec-examples/context/class-light-reflection.json` |

**Colour words keep their colour.** Write the label plainly (「초록불」「빨간불」「청팀 · 백팀」「금 · 은 · 동」): the build paints that head, badge or card in the colour it names instead of the deck's next colour (`shared/design/meaning.py`). Never recolour them by hand, and in a page you make yourself do the same.

**No blanks, ever.** Never write `[학교명]`, `(학교명 입력)`, `(…을 입력하세요)`, `[날짜]`, `20XX`, `OO초`, `OOO`, `○○학교`, `(예시)`, `(미정)`, `000-0000` in a spec. Fill with a plausible example value (today's date, 2026학년도 / the current school year, generic 「우리 학교」·「3학년」, a real date, a round figure) and name each one in `"fillins": ["행사 날짜 2026. 12. 4.(금)", "참가비 5,000원", ...]` (top-level list): the build notes it once in the first slide's speaker notes and prints the 「바꿔 넣을 곳」 list for the last message. A leftover slot is a FAIL (HTML review and `pptx_check.py`); so are three or more 「확인 필요」-type cells and a 「교사 초안」 stamp on a slide. **The user wins:** 「양식으로 해 줘」「빈칸 있는 틀로」「서식만」 -> spec `"template_blanks": true` (top level): all blanks stay, are reported as 「바꿔 넣을 곳」, and the build prints one caution line (`pptx_check.py --allow-blanks` for a lone file).
Rules: one message per slide, <= 330 characters of text on a slide (a `panel` may hold about 560; these are per-screen limits, so content that does not fit goes to another slide, it is not cut), no emoji (stripped; the one exception is a 유치원-초3 lesson, where one emoji in front of a word is that word's picture). Text is projection-sized (>= 28px) — never ask for smaller. Do not invent statistics about the world; a world fact you cannot verify is left out and named in the last message (never 「확인 필요」 on a slide). No student names/photos.
Build errors are lists of 「고칠 곳」: fix exactly those and rerun. A date written with its weekday (`2026. 12. 5.(토)`, `12월 5일(토)`) is checked against the calendar; a wrong weekday stops the build.
Old `fire slides/lesson-deck/<skin>` (3 skins) still works but is the **lowest priority**: use it only if the teacher names a legacy look.

## Design language (automatic)
**The look follows the room and the topic, not a template.** Write `"audience"` exactly as the user said it (「초등학교 2학년」, 「어르신」, 「고1」, 「교직원」): young children (유치원-초3) and 초4-6 get larger type, rounder shapes, a light friendly look and the topic's icon or drawing on the cover; 유치원-초3 also get crayon-bright colours (three clear hues from the topic or the seed, never neon), list cards tinted in their own tone, word pictures and a large answer slide; 어르신 get the largest type on a light, high-contrast page; nobody gets neon. For a young room also write for it: 3 items or fewer per slide, short sentences in the children's register (~해요), and draw the thing itself (`title.shapes`, `diagram`). The deck's colours come from the topic when it has one (lava is warm, the sea is blue: `title` / `subject` words) and always from the design system: one main colour plus up to two marker colours for badges, card heads and chart series. In the .pptx **every slide type has several layouts and the build picks one from the content and the seed** (a list as rows, tiles or beside a colour field; steps as a track, block arrows or a ladder; a cover as a block, a band or plain; two sides as cards or facing fields; a 항목 | 내용 table as label tiles), never the same one twice running; `"layout": "bullets.grid"` forces one. **Icons are picked by meaning** (`scripts/deck_icons.py`, Lucide, ISC): a line that names a thing (전화, 지도, 달력, 화산 ...) gets its icon in the web deck and as an editable outline in the .pptx; a list shows icons only when every line has its own, otherwise numbers. Override with `"icons": ["phone", "지도", ...]` (Lucide names or Korean words) or `icon` on a step / card. Nothing on a .pptx slide is under 14pt (16pt for young and older audiences); text that would need less is reported as too long.
`scripts/deck_style.py` maps purpose + mood + subject to one of the 12 shared styles (`shared/design/styles.py`) and a palette; each style has its own composition (title treatment, card, emphasis, background motif, transition, preferred layout families). Every slide type has 2-4 layout variants (asymmetric splits, full-bleed type, bento cards, editorial rows, numbered steps, comparison panels); the picker never repeats a layout twice in a row. Use the user's logo/template colours first (`design.palette_from`; means, not our design). `slides_review.py` and `check` WARN when correct/wrong or chart colours look alike to colour-blind eyes (add shapes or text). Custom flair is allowed per slide and sandboxed: `"flair":{"css":"...","svg":"<svg>..</svg>"}` (no external urls, scripts, fixed positioning; css is scoped to that slide). Use it where the topic needs a drawing or an arrangement the slide types cannot make; the review gate still applies.

## Review gate (`scripts/slides_review.py`)
**no placeholders left** (`placeholders.py`: `[대괄호]`, `20XX`, `OO`, `○○`, `000`, 학교명 ... FAIL) · **unknowns** (「확인 필요」-type filler 1-2 WARN, 3+ FAIL; 「교사 초안」 stamp FAIL; example note repeated or missing WARN) · External requests 0 · contrast >= 4.5 on real pixels · text >= 28px · overflow / safe margin / keep-all · not empty · **clutter caps** (elements <= 36, icons <= 3, big colours <= 5) · no 3 identical layouts in a row. Compare decks: `slides_review.py --compare a.html b.html` (distance >= 0.35).

## PowerPoint (.pptx) review - `scripts/pptx_check.py deck.pptx --spec deck.json --render review/`
`deck.py --pptx` builds the file, **shrinks text that would overflow its box** (never below 60% / 12pt; same metrics as the check, `pptx_fit.py`), then runs `pptx_check`: placeholders FAIL · unknowns (「확인 필요」 on three or more places FAIL, a 「교사 초안」 stamp FAIL, the example note on more than one slide WARN) · text fit (estimate) FAIL · shapes inside the slide · no empty placeholder · **no empty-looking slide** (`pptx_fill.py`: a body slide whose content covers < 6 % of the slide or stops above 60 % of its height FAILs: add content or merge it) · **text large enough to project** (any text under 11pt FAILs, under 14pt is a NOTE) · **not one layout all the way** (NOTE when most body slides are plain text lists, on any .pptx). A FAIL on text fit means: shorten or split that slide in the spec and rebuild. The build ends with `READY file` only when every check passes, otherwise `NOT DONE`.
**Look at it.** `--review DIR` also draws PNGs: with **LibreOffice** installed it is a real rendering; otherwise it is an **approximate** preview drawn from the pptx itself (`pptx_draw.py`: shapes, lines and arrows, pictures, tables, native charts, groups, master art; red outline = estimated overflow). It works on any .pptx, so two decks can be compared with the same eyes. Always tell the teacher which one it was. LibreOffice is large (about 350MB download, 5-10 minutes): offer it once with the size (`py shared/tools/ensure.py libreoffice`, install only after a yes, `--yes-libreoffice`); declining is fine.
**Last message** (pipeline.md, Final checkpoint): file path, how to open it, check result, the 「바꿔 넣을 곳」 list.

## Absolute rules
1. **No student info** on slides. Example names are fictional.
2. **Facts**: a world fact you are unsure of is left out and named in the last message; the user's own unknowns are example values in `"fillins"` (「Unknown facts」). Sources of numbers go to the note.
3. **Copyright is advisory, not blocking** (`references/legal-advisory.md`): teacher's own images/quotes go in with one line of advice.
4. **Offline**: no external requests; fonts are embedded Noto Sans/Serif KR; old Chrome safe (no `?.` `??` `replaceAll` `:has` `aspect-ratio`).
5. Full-screen button and notes (N) stay; notes hidden by default.
