# 하네스 업그레이드 기록 (2026-11-20)

목표: 가장 좋은 모델의 판단을 하네스 안에 「순서 · 기준 · 예시 · 자동 점검」으로 적어 넣어서, 약한 모델(Sonnet·Haiku·무료 모델·Codex)이 따라 해도 비슷한 결과가 나오게 한다.
범위: teacher-studio(입구·방향·공정·기획·웹 앱), teacher-game, teacher-motion, teacher-class-tools, teacher-data, teacher-law. teacher-slides·teacher-docs·docs/training은 손대지 않았다(읽기만).

## 결론 먼저

- **속도 점검이 더는 PC 탓으로 실패하지 않는다.** 예전에는 이 PC에서 모든 게임이 「프레임 속도」에서 FAIL이었다. 이제는 「페이지 자신이 한 장면에 쓰는 일의 양」을 재고, 같은 실행 안에서 PC 상태를 먼저 재서 PC가 느리면 주의(WARN)로만 알린다.
- **게임은 AI가 하는 일이 절반으로 줄었다.** 실제 실행(Sonnet)에서 대화 횟수 2번, 비용 $0.23(전 $0.49), 도우미 에이전트 0개, 마지막에 제대로 된 완료 답변. 다만 이 PC가 다른 작업으로 매우 바빠서 벽시계 시간은 823초였다(아래 표와 주의).
- **법 질문은 이제 조문 원문을 실제로 읽는다.** 국가법령정보센터에서 조문 글과 시행일을 한 번에(법령 하나에 약 2초) 가져오는 길을 찾아 넣었다. 답은 51초, $0.19(전 55초, $0.27), 글 분량은 절반.
- **입구 규칙은 「세 번의 결정」으로 바뀌었다.** Haiku 점수는 0.918 → 평균 0.961(5회), Sonnet은 0.991 → 0.991(47건) / 0.993(59건).
- 아직 남은 것: 법 질문 비용은 여전히 일반 AI($0.06)보다 비싸다. 게임의 벽시계 시간은 조용한 PC에서 다시 재야 한다.

## 스킬별로 무엇을 왜 바꿨나

### 공통 속도 점검 (`shared/juice/juice_lint.py`, 게임·수업 도구가 같이 씀)
- 문제: 「CPU를 4배 느리게 하고 초당 30장면」 기준이 이 PC에서는 항상 실패(2~22장면). 원인은 게임이 아니라, 화면 없는 크롬이 그래픽 카드 없이 그림을 그리기 때문이었다(같은 게임이 그래픽 카드를 켜면 2배 빨라짐).
- 바꾼 것
  1. **기준을 「페이지 자신의 일」로**: 스크립트·모양 계산·배치에 한 장면당 쓴 시간(크롬이 직접 알려 주는 값)이 33ms 이하면 PASS. 예시 게임은 약 10ms.
  2. **같은 실행 안에서 PC를 먼저 잰다**: 거의 빈 움직이는 페이지의 장면 수와, 정해진 계산이 실제로 몇 배 느려졌는지. 빈 페이지조차 45장면이 안 나오거나 느려짐이 6.4배를 넘으면 「이 PC는 지금 판정할 수 없음」.
  3. **FAIL은 두 조건이 모두 맞을 때만**: 페이지 자신의 일이 기준을 넘고 + PC가 판정 가능할 때. 그 밖에는 WARN.
  4. 장면 수(fps)는 숫자로 계속 보여 주되, 혼자서는 실패시키지 않는다. 클릭 반응도 같은 원칙.
- 확인: 조용할 때 `PASS 10.5ms / WARN 14fps`, 다른 작업이 겹쳤을 때 `WARN(PC가 바빠 판정 불가)`로 나왔고 둘 다 빌드는 통과했다. 판정 규칙은 단위 테스트로 고정(`tools/test_fable_upgrade.py`).
- 한계: 그림 그리기 자체가 무거운 꾸밈(큰 흐림 효과 등)은 이제 WARN으로만 잡힌다. 실제 교실 PC에서 한 번 보는 것이 가장 확실하다.

### teacher-game
- 약한 모델이 틀리던 곳: 안내문이 17KB로 길고 단계가 5개 + 하위 단계, 명령이 3개(만들기·점검·디자인 점검), 도우미 에이전트에게 넘기고 「만드는 중」으로 끝남, 문제 품질은 글로만 부탁.
- 바꾼 것
  1. `SKILL.md`를 **6단계 한 장(10KB)**으로 다시 씀: 정하기 → 문제 표 → 설계 쓰기 → 명령 하나 → 결과에 따라 행동 → 마지막 답. 설계 예시 1개와 「요청 → 방식」 표를 본문에 넣어 다른 문서를 열 일이 줄었다. 자세한 내용은 `references/advanced.md`로 옮김.
  2. **명령 하나로**: `build.py --spec … --out … --review`가 만들기 + 점검 + 화면 모음 사진까지 한다. 출력은 고칠 줄(FAIL·WARN)과 결론만 보여 주고(전에는 45줄), 끝에 `READY 경로` 또는 `NOT READY`를 찍는다.
  3. **문제 품질 관문**(`specs.content_review`): 정답만 유난히 긴 보기, 「모두 정답」 보기, 해설 없음, 같은 문제 반복, 칠판에서 읽기 긴 문장·보기, 「아닌 것은?」 과다, 팀전인데 타이머 없음. 걸리면 1초 만에 멈추고 고칠 곳을 알려 준다. 선생님이 준 문제 그대로일 때는 `--ok-content`로 끈다(사용자가 이긴다).
  4. 설계 파일이 없거나 깨졌을 때 오류 덩어리 대신 「고칠 곳」 한 줄.
  5. 「문제 품질 기준 7가지」와 「화면 점검 5가지」를 본문에 번호로 적음.

### teacher-law
- 문제: 일반 AI보다 비싸고, 두 번의 비교 모두 조문 원문을 열지 못했다.
- 바꾼 것
  1. `law_fetch.py --articles "저작권법:25,35의5"`: 법령 페이지에서 번호를 읽고 본문 주소에서 **조문 글 + 시행일 + 링크**를 가져온다. 한 번 시도, 다시 시도 없음, 막히면 30분 기억.
  2. `SKILL.md`를 **4단계**로(7.8KB → 6.2KB): 분류 → 조문 한 번에 읽기 → 꼭 필요할 때만 검색 1번 → 답 카드. 종류별 「볼 조문」 표를 본문에 넣어 다른 문서를 열지 않게 함.
  3. 답 카드는 **250단어 이내**, 근거 3줄 이내, 카드 뒤에 덧붙이는 글 금지. 「좋은 답 5가지 기준」 추가.
- 결과(같은 질문, Sonnet): 근거에 「저작권법 제25조 (시행 2026-10-29)」처럼 공식 원문과 시행일이 들어갔다. 전에는 보조 자료 링크 3개였다.

### teacher-studio (입구·웹 앱)
- 문제: 규칙이 두 군데(R0~R5와 공정 1~7)에 나뉘어 겹쳤고, Haiku가 「카운트다운 화면」을 게임으로, 「속력 계산기」를 게임으로, 「알아서」인데 보기를 내놓는 일이 있었다.
- 바꾼 것: **세 번의 결정**으로 정리했다. ① 안전한가 ② 어디로 보낼까(표 13줄, 첫 줄 우선) ③ 첫 답을 어디서 멈출까(표 9줄, 첫 줄 우선). 헷갈리던 경계는 표 안에 예시로 못 박았다(카운트다운 화면 ≠ 타이머, 계산기 ≠ 게임, VR·서버 앱은 우리 도구가 아님, 「알아서」가 있으면 물음표 0개).
- 다른 작업자가 넣은 문서(teacher-docs)·발표 맥락 줄은 그대로 살렸다.
- 웹 앱 안내(`references/webapp.md`)에 「좋은 웹 앱 6가지 기준」 추가(첫 화면 5초, 그 수업의 실제 내용, 조작하면 바로 결과 등).

### teacher-data · teacher-class-tools · teacher-motion
- data: 「열 모양 → 분석 종류」 고르는 표와 「좋은 보고서 5가지 기준」 추가. 직접 4개 명령으로 끝내라고 명시.
- class-tools: 숫자가 이미 있으면 묻지 않는 규칙, 「좋은 도구 4가지 기준」, 마지막 답 모양. 속도 점검 설명 갱신.
- motion: 맨 위에 4단계 요약과 「좋은 30~40초 영상 6가지 기준」(한 장면 한 생각 12단어 이내, 첫 3초에 눈길, 마지막 화면 2초 유지 등) 추가. 나머지 본문은 그대로다(다음에 줄일 후보).

- **시간은 믿을 수 없는 조건이었다.** 이번 실행 동안 이 PC에서 다른 작업자들의 화면 없는 크롬·빌드가 계속 돌아, 평소 55초 걸리는 게임 점검이 5~10분씩 걸렸다. 게임은 설계 파일이 1분 33초, 게임 파일이 2분 9초에 만들어졌고 나머지 11분은 점검이 끝나기를 기다린 시간이다. 조용한 PC에서 다시 재야 한다(**확인 필요**).
- 참고: 실행이 끝난 뒤 같은 설계 파일로 그 한 명령(만들기 + 점검 + 화면 사진)을 다시 돌리니 121초였다(그때도 PC는 바빴다). AI가 일한 165초와 더하면 **약 5분으로 추정**되지만, 한 번에 잰 값이 아니라 어림이다. 이 재실행에서는 화면 사진 점검이 돌았고 「배경 장식이 글자 뒤를 지나감, 글자 대비 4.46」을 지적했다. 즉 실제 실행에서는 사진 점검이 빠진 탓에 디자인 흠 1~2곳이 고쳐지지 않고 나갔다.
- `tools/sync_shared.py`(공용 복사 + dist zip 다시 만들기)는 이 작업 환경의 권한 장치가 막아서 **돌리지 않았다**. `shared/juice`의 복사본 4개는 손으로 똑같이 맞췄고 테스트가 확인한다. `dist/*.zip`은 옛 내용이므로 `py tools/sync_shared.py` 후 `py scripts/setup.py --agent claude-code`를 한 번 돌려야 설치본에 반영된다.
- 게임: 10문항(OX 2 + 4지선다 8), 3팀, 25초, 문항마다 해설. 점검 44개 통과, 주의 2개(한 글자 줄바꿈, PC 느림).
- 법: 결론이 「가정통신문은 수업 목적 예외에 들기 어렵다」로 더 구체적이 됐다. 내용의 법적 정확성을 제가 따로 검증한 것은 아니다.

## 슬라이드 쪽 제안 (teacher-slides 담당자에게, 저는 고치지 않았어요)
1. **빈칸 관문**: 통합 점검에서 `pptx_check.py`를 `--spec` 없이 돌리면 `[학교명]`이 통과됐다. 지금 코드는 `--spec`이 없어도 빈칸을 FAIL로 보는 것처럼 읽히는데(108줄 부근), 실제 `[학교명]` 파일로 한 번 더 확인해 주세요. `deck.py`가 `.pptx`를 만든 직후 `pptx_check`를 항상 스스로 돌리면 약한 모델이 건너뛸 수 없어요.
2. **빈칸을 처음부터 안 만들기**: v2 비교에서 빈칸 25곳이 가장 큰 손실이었어요. 「오늘 날짜·학년도는 채우고, 모르는 고유 이름은 `fillins`에 모아 마지막 답에 『바꿔 넣을 곳』으로 보여 준다」를 맥락 예시(`spec-examples/context/*.json`) 모두에 반영하면 좋아요.
3. **한 명령 + 짧은 출력**: 게임처럼 `deck.py`가 만들기 + 점검 + 접촉 시트를 한 번에 하고 FAIL/WARN/READY만 찍으면 대화 횟수와 비용이 줄어요.
4. **내용 관문**: 장마다 제목이 주장 한 문장인지, 한 장 글자 수, 같은 배치 3장 연속, 발표자 메모 유무를 `content_review` 식으로 미리 잡으면 좋아요(걸리면 1초 만에 멈춤, `--ok-content`로 끔).
5. `SKILL.md` 맨 위에 「6단계 요약 + 설계 예시 1개 + 좋은 발표 기준 5~7개」를 두고 나머지는 references로.
6. `tools/test_direction.py`의 입구 사례 수 검사(47)가 59로 바뀐 사례 파일과 어긋나 실패해요(문서 작업 쪽 변경).

## 한계 (정직하게)
- 실제 실행은 사례마다 한 번이다. 시간은 PC 과부하로 비교할 수 없고, 비용·대화 횟수·결과물만 비교할 수 있다.
- 12개 예시 게임 전체와 수업 도구 5개를 새 속도 점검으로 다시 돌리지는 않았다(2개만). 조용한 PC에서 한 번 돌려야 한다.
- 입구 평가는 「이렇게 하겠다」는 말을 채점한다. Codex(GPT)는 돌리지 않았다.
- motion 본문, data의 한 명령화(프로파일 → 분석 → 보고서 → 점검을 하나로)는 다음 차례로 남겼다.
